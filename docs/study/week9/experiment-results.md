# 파라미터 실험 — 캐시 크기가 provider 호출을 결정한다

> 9주차 금요일. 목요일에 찍어둔 로그를 그대로 두고 설정값 하나만 바꿔서 관찰.

---

## 1. 실험 조건

바꾼 것은 하나다.

```bash
--rpc-cache.max-blocks 5000   # 기본값
--rpc-cache.max-blocks 10     # 실험값
```

나머지는 동일: `--dev --dev.block-time 1s`, 같은 datadir, 같은 바이너리.

측정 방법은 블록을 하나씩 조회하고 `study` 로그가 뜨는지 보는 것.

```bash
cast block-number -r http://localhost:8545     # 최신 번호
cast block <번호> -r http://localhost:8545     # 하나씩 조회
```

로그는 다른 창에서:

```bash
tail -f ~/.cache/reth/logs/dev/reth.log | grep --line-buffered "DEBUG study:"
```

---

## 2. 결과 — 경계가 움직였다

| 설정 | 최신에서 0~50블록 뒤 구간 |
|---|---|
| `max-blocks 5000` (기본, 목요일) | **전부 0줄** — 캐시에서 끝남 |
| `max-blocks 10` (금요일) | **2줄** — provider까지 내려감 |

목요일에 기본값으로 돌렸을 때는 최신-0부터 최신-100까지 전부 0줄이었다. 그때 provider가 불린 것은
**이전 프로세스가 만든 블록(0~252)** 뿐이었고, 그건 캐시 크기 때문이 아니라 프로세스 재시작 때문이었다.

캐시를 10으로 줄이자 **같은 구간이 전부 provider 호출로 바뀌었다.**

> 캐시 크기가 provider 호출 여부를 직접 결정한다. 파라미터 하나로 호출 경로가 갈린다.

### 측정의 한계

`tail -f`를 요청보다 늦게 띄워서 **블록 번호와 로그의 짝을 정확히 맞추지 못했다.**
6개 요청 중 4개 쌍(2줄씩)이 확인됐고, 나머지 2개는 tail 시작 전에 지나갔다.
"경계가 정확히 최신-10인가"는 확인하지 못했고, "기본값에서는 0줄이던 구간이 2줄이 됐다"까지가
확실한 결론이다.

## 3. 개념 정리 — 캐시와 인메모리는 별개다

실험보다 이쪽이 오늘의 수확이다. 처음엔 둘을 같은 것으로 착각했다.

| | 캐시 | 인메모리 |
|---|---|---|
| 누가 | RPC 계층 (`EthStateCache`) | 엔진 |
| 왜 | 같은 블록 재요청을 빨리 처리 | 아직 디스크에 안 내려간 최신 블록 |
| 들어오는 조건 | 블록 생성 시 **+ 조회로 읽어왔을 때** | 블록 생성 시 |
| 나가는 조건 | **새 블록에 밀려서** (LRU) | **디스크에 써져서** |
| 크기 | `--rpc-cache.max-blocks` (5000) | `--engine.persistence-threshold` (7) |

**캐시에서 나가는 이유는 디스크 저장과 무관하다.** 자리가 없어서 밀려날 뿐이다.
두 규칙이 독립적이라 네 조합이 모두 가능하다.

| | 캐시 | 인메모리 | 예 | 로그 |
|---|---|---|---|---|
| ① | O | O | 방금 만든 최신 블록 | 0줄 |
| ② | **O** | **X** | 오래된 블록을 조회해서 캐시에 올라옴 | 0줄 |
| ③ | X | **O** | 캐시가 인메모리보다 작을 때 | **1줄** |
| ④ | X | X | 아무도 안 물어본 오래된 블록 | 2줄 |

②는 목요일에 이미 관찰했다 — 블록 50 첫 조회는 2줄, 두 번째 조회는 0줄.
디스크에서 읽어온 블록도 캐시에 올라간다는 뜻이고, 코드로도 확인된다
(`cache/mod.rs:632-635`가 provider 결과를 `on_new_block`으로 캐시에 넣는다).

> **인메모리는 항상 최신 쪽 연속 구간**이지만,
> **캐시는 조회 패턴에 따라 구멍이 뚫린 채 흩어질 수 있다.**

---

## 4. 미관찰로 남긴 것

**③ (캐시 X, 인메모리 O = 1줄)은 이번 주에 한 번도 관찰하지 못했다.**

이론상 `--rpc-cache.max-blocks`를 `--engine.persistence-threshold`(7)보다 작게 하면
그 사이 구간이 벌어져서 나타나야 한다.

```
--rpc-cache.max-blocks 2   →  최신-3 ~ 최신-7 구간이 "캐시엔 없고 메모리엔 있는" 상태
```

시도하지 않은 이유는 그 구간이 초당 한 블록씩 움직여서 조회 타이밍을 맞추기 어렵고,
얻을 정보가 이미 세운 모델의 확인 하나뿐이기 때문이다. 다음에 필요하면
`--dev.block-time`을 크게 잡아(예: `30s`) 구간을 고정한 뒤 조회하면 된다.

---

## 5. 이번 주 실험에서 배운 것

1. **파라미터 하나로 호출 경로가 바뀐다.** 캐시 5000 → 10으로 같은 요청이 provider까지 내려갔다.
2. **"메모리에 있다"가 두 가지를 뜻한다.** RPC 캐시와 엔진 인메모리는 주인도, 들어오고 나가는
   규칙도 다르다.
3. **측정 도구를 먼저 갖춰라.** `tail -f`를 늦게 띄워서 짝을 못 맞췄다. 요청을 보내기 전에
   관찰 창부터 띄워야 한다.
4. **`cast`를 쓰면 된다.** curl + 16진수 변환 + JSON 파싱을 손으로 할 이유가 없다.
   `cast block <번호> -r <url>` 한 줄이면 끝.
